### Prompt 2 — Shared schema & tracking fields

```
In src/common/schema.py, define the canonical GlucoFlow reading schema using pydantic v2.

A CanonicalReading has:
- patient_id: str
- event_time: datetime (UTC, timezone-aware)
- glucose_mgdl: float | None  (None if out of range / non-numeric)
- glucose_flag: Literal["in_range","low","high","invalid","out_of_range"] 
- source_system: Literal["shanghai","simglucose","dexcom_messy"]
- batch_or_stream: Literal["batch","stream"]
- ingest_time: datetime (UTC, set at ingestion)
- lineage_id: str (uuid4)
- raw_payload: dict  (original row, for audit)

Rules:
- Valid glucose range is 40–400 mg/dL. Outside that but numeric -> flag "out_of_range", keep value.
- "Low" string -> glucose_mgdl=None, flag="low". "High" -> None, flag="high".
- Non-numeric/missing -> None, flag="invalid".
Add a factory classmethod `from_raw(cls, row: dict, source_system, batch_or_stream)` that applies these rules and auto-sets ingest_time and lineage_id.
Write pytest tests in tests/test_schema.py covering: normal value, Low, High, out-of-range (e.g. 500), and garbage string.
```

### Prompt 3 — simglucose synthetic generator

```
In src/generators/synthetic_gen.py, write a generator that uses the simglucose package to produce CGM data.

- Generate data for 5 adult patients (use simglucose's built-in adult patient presets, e.g. adult#001 through adult#005).
- 14 days per patient, sensor sampling every 5 minutes.
- Include realistic sensor noise (use simglucose's default CGM sensor model, e.g. Dexcom).
- Output one CSV per patient to data/samples/synthetic/ with columns: patient_id, timestamp (ISO8601 UTC), glucose_mgdl.
- Also print a summary per patient: number of rows, min/max glucose, % readings in 70–180 range.
- Make it runnable as `python -m src.generators.synthetic_gen`.
If the simglucose simulation API differs from what you expect, read the installed package's examples and adapt. Add a short docstring citing simglucose (UVA/Padova T1DM simulator).
```

> ⚠️ simglucose's simulation API can be fiddly (it runs a controller/scenario loop). Tell your coder explicitly: *"If the full simulation loop is complex, use simglucose's CGMSensor + a basic meal scenario to produce a glucose trace — the goal is realistic 5-minute readings with sensor noise, not a perfect closed-loop sim."*

### Prompt 4 — Dexcom-style "messy" CSV generator

```
In src/generators/messy_dexcom_gen.py, write a generator that takes clean readings (reuse the synthetic CSVs from data/samples/synthetic/) and produces a "messy" Dexcom Clarity-style export to data/samples/messy/.

Replicate these real-world quirks:
1. Mixed event rows: a column "Event Type" with values like "EGV" (glucose), "Calibration", "Insulin", "Carbs". Only EGV rows have a glucose value.
2. For EGV rows where glucose < 40, write the string "Low" instead of a number. Where > 400, write "High".
3. Add a few metadata/header rows at the top (device, transmitter serial, export date) that are NOT part of the tabular data — simulate the real Clarity CSV preamble.
4. Column names mimicking Clarity: "Index", "Timestamp (YYYY-MM-DDThh:mm:ss)", "Event Type", "Event Subtype", "Glucose Value (mg/dL)", "Transmitter ID".
5. Inject ~2% duplicate rows and ~1% rows with blank glucose on an EGV row.

Make it runnable as `python -m src.generators.messy_dexcom_gen`.
Add a comment block noting these column names are approximations and must be verified against official Dexcom Clarity export docs before production use.
```

### Prompt 5 — AWS infrastructure (buckets + IAM)

```
In infra/, create a bash script setup_aws.sh that provisions Day 1 AWS resources using the AWS CLI. It must be idempotent (safe to re-run).

Create 4 S3 buckets using names from env vars BRONZE_BUCKET, SILVER_BUCKET, GOLD_BUCKET, QUARANTINE_BUCKET:
- Enable versioning on all 4.
- Block all public access on all 4.
- Add a lifecycle rule on bronze to expire objects after 30 days (demo cost control).

Create a least-privilege IAM policy document (infra/glucoflow-policy.json) granting s3:PutObject, s3:GetObject, s3:ListBucket ONLY on these 4 buckets.

Also create infra/teardown_aws.sh that empties and deletes all 4 buckets (with a confirmation prompt).

Read bucket names and region from a .env file. Print each resource as it's created. Do NOT hardcode account IDs or credentials.
```

> ⚠️ S3 bucket names are **globally unique**. Tell your coder to suffix bucket names with something unique (e.g. `glucoflow-bronze-<yourinitials>-<random>`). Set these in `.env` before running.
